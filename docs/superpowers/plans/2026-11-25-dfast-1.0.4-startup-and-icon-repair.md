# DFast 1.0.4 — Startup Crash & Icon Repair Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the shipped app open again (it dies on the splash screen) and repair the broken launcher icon, then publish that as release `1.0.4`.

**Architecture:** Three independent, verifiable repairs on top of `471e6bd`: (1) the nav host in `activity_main.xml` names a class that does not exist, so `MainActivity.setContentView` throws during inflation; (2) the adaptive icon background resolves to the inherited orange `icon_bg` in night mode, and the foreground vector's group matrix translates the mark up and left of centre; (3) the version is 1.1.0 and must become 1.0.4. Each repair is a small resource/edit change and is checked statically (no emulator is available in this environment), then the whole APK is verified by the CI build before publishing.

**Tech Stack:** Android (Gradle, Kotlin, AGP), AndroidX Navigation, adaptive icons (VectorDrawable/layer-list/PNG mipmaps), GitHub Actions.

**Spec:** diagnosis below, derived from commit `2c67532` ("feat(ui): rebuild DFast as Flux…") against its parent, plus the user's screenshot of the splash screen.

## Diagnosis

Symptom from the device: the launcher shows a white rounded icon containing an orange square with an off-centre pale chevron, and the app shows that same splash for a moment, then closes.

Ranked hypotheses, with the falsifiable prediction each made:

1. **`FragmentContainerView` cannot instantiate its `android:name`.** `activity_main.xml` declares `android:name="androidx.fragment.app.NavHostFragment"`. That class does not exist; `NavHostFragment` lives in `androidx.navigation.fragment` (the same layout's pre-redesign version used that package, and `activity_settings`, `activity_terminal` and `activity_share` still do). *Prediction: restoring the navigation package string removes the crash, and `supportFragmentManager.findFragmentById(R.id.frame_layout) as NavHostFragment` in `MainActivity:136` then stops finding `null`.* **Confirmed: this is the cause.** The crash happens inside `setContentView`, i.e. exactly after the splash is drawn and before the first frame, which is what the device shows.
2. **A missing/renamed view id** would throw `NullPointerException` after `setContentView`. *Prediction: a crash with a view id in the stack trace, after the window is up.* Rejected: the release compiles against `R.id`, and a Kotlin type mismatch would be a compile error; the app never reaches `onCreate`'s body.
3. **A malformed new theme/style** would fail at `setTheme`. *Prediction: `Resources$NotFoundException` even earlier.* Rejected: `Theme.DFast` and `dfast_styles.xml` are referenced successfully by the CI build's resource-merging stage, and the splash screen itself renders with the new colours.

Icon symptom, same two-file analysis:
- `drawable/ic_launcher_background.xml` fills the adaptive background with `@color/icon_bg`, and `values-night/colors.xml` still carries the *inherited* Ember orange `#FF5A36` for that name. In night mode (the screenshot is dark) the icon background turns orange while everything else is indigo.
- `drawable/ic_launcher_foreground.xml` puts the mark in a group with `pivot 54,54`, `scale 1.35` **and** `translateX=16, translateY=16`. VectorDrawable applies `translate` after scaling around the pivot, so the mark's centre (34,27) lands at (43,33.5) instead of (54,54): the chevron sits up-left, which is the "glitch" the user sees.
- The pre-adaptive PNG mipmaps (API 24–25, plus some launchers) are still the previous orange "D + arrow" artwork.

## Global Constraints

- Package ids stay `dfast.app`; Java/Kotlin packages stay `com.deniscerri.ytdl.*`; GPLv3 attribution unchanged.
- Only these links may ship: `https://github.com/MenuM7D/dfast` and `https://t.me/m7d_devvv`.
- No local Gradle/JDK build (the sandbox cannot hold a Gradle build): every build check runs on GitHub Actions.
- Version must be `versionName 1.0.4`, `versionCode 1000400` (scheme: major×1000000 + minor×10000 + patch×100).
- The Flux palette is unchanged: icon background `#4A3FE0`, icon foreground `#FFFFFF`.

## Review Focus

- **MainActivity opens at all** — a user who taps the icon must reach Home; the class name is the single point of failure.
- **Icon in dark mode** — a phone in night mode must not render an orange tile; `icon_bg` is resolved per configuration, so both `values/` and `values-night/` are checked.
- **Icon geometry** — the mark must be optically centred inside the 72dp adaptive safe zone, not merely present.
- **API 24–25 devices** — those read the PNG mipmaps, so the icon there must match the adaptive one, not the old Ember art.
- **Version ordering** — a user upgrading from 1.0.2 must keep the same signature and get versionCode 1000400; the stray 1.1.0 build (versionCode 1010000) is higher, so it is called out to the user rather than silently hidden.

**Files:**
- Modify: `dfast/app/src/main/res/values-night/colors.xml:2`

**Interfaces:**

- Produces: an adaptive icon whose background is `#4A3FE0` in every configuration and whose foreground chevrons are centred at (54,54) in the 108×108 viewport.

- [ ] **Step 1: Assert the palette defect**

Run: `grep -n 'icon_bg' dfast/app/src/main/res/values-night/colors.xml`

- [ ] **Step 2: Set the night token to the brand indigo**

```xml

```

- [ ] **Step 3: Draw the foreground centred, with no compensating translate**

Paths are the mark's own coordinates mapped by `p' = 54 + (p − (34,27)) × 1.25`, so the group needs no matrix at all:

```xml

    android:pathData="M39,32.75 L54,47.75 L69,32.75 L75.88,39.63 L54,61.5 L32.12,39.63 Z" />
<path android:fillColor="@color/icon_fg" android:fillAlpha="0.72"
    android:pathData="M39,46.5 L54,61.5 L69,46.5 L75.88,53.38 L54,75.25 L32.12,53.38 Z" />
```

- [ ] **Step 4: Regenerate the legacy PNG mipmaps**
